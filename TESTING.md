# Автоматическое тестирование

Тесты проверяют отдельные сценарии API, интерфейса и базы данных. Набор пока не охватывает весь проект.

## Инструменты

- **Jest** запускает тесты и проверяет результаты.
- **Supertest** отправляет запросы к Express для проверки API.
- **Selenium WebDriver** управляет Chrome в фоновом режиме для проверки интерфейса.
- **Docker Compose и PostgreSQL 18** предоставляют отдельную тестовую базу.

Перед запуском установите зависимости командой `npm install`. Для браузерных тестов нужен Chrome; Selenium Manager при первом запуске может скачать подходящий драйвер. Для интеграционных тестов нужен запущенный Docker.

## Тесты API

```sh
npm test
```

Файл `tests/api.test.js` проверяет доступность health check, отсутствие токена, права клиента, получение деталей заказа, проверку статуса оплаты и защиту операций с вариациями товаров. База заменяется подставными ответами, поэтому эти тесты не проверяют реальные SQL-запросы и не изменяют рабочую базу.

## Тесты интерфейса

```sh
npm run test:browser
```

Тесты из `tests/browser` проверяют ошибку входа, вход и переход к заказам, просмотр и изменение заказа, просмотр доставки и создание варианта товара. Для изоляции используется локальный тестовый сервер с подставными данными; реальная база и работающий сервер приложения не требуются.

Асинхронные сценарии задают задержку ответов тестового сервера и ждут появления результата или закрытия формы. Проверяется также сообщение при ошибке загрузки заказов. Это воспроизводимые проверки асинхронности, а не намеренно нестабильные тесты.

## Интеграционные тесты PostgreSQL

```sh
docker compose -p store-admin-tests -f docker-compose.test.yml up -d --wait
npm run test:integration
docker compose -p store-admin-tests -f docker-compose.test.yml down
```

Контейнер запускает отдельную базу `store_test` на `127.0.0.1:55432` и загружает `schema.sql`. Тесты проверяют подключение и ограничение уникальности бренда. Изменения теста выполняются в транзакции с откатом. Данные контейнера временные и удаляются при его остановке; рабочая база не используется.

## Проверки намеренных ошибок

Тесты специально создают ошибочные условия и проверяют ожидаемую реакцию:

- Неверный пароль и ошибка загрузки заказов отображаются в интерфейсе.
- Запрос без токена и действия пользователя без нужных прав отклоняются API.
- Недопустимый статус оплаты и отрицательный остаток отклоняются API.
- Повторное создание бренда с тем же названием отклоняется PostgreSQL.

Эти тесты должны проходить: ошибка является входным условием, а успешная проверка означает, что приложение или база отреагировали ожидаемым образом.

## Применённые техники тест-дизайна

- **Классы эквивалентности:** отсутствующий, некорректный и просроченный токены; допустимые статусы оплаты.
- **Граничные значения:** остатки −1, 0 и 1 в API; в PostgreSQL проверены остаток, равный резерву, и остаток ниже резерва. API-тесты используют подставную базу.
- **Таблица решений:** проверены сочетания роли и принадлежности адреса для администратора, менеджера, клиента и курьера. Это выбранные сочетания, а не полная матрица всех маршрутов.
- **Переходы состояний:** проверено, что маршрут изменения статуса заказа вызывает запись истории и обновление заказа. Запросы к базе здесь подставные; допустимость переходов и атомарность операций не проверяются.
- **Причина и следствие:** ошибки авторизации и запросов и повторная загрузка после ошибки проверяются по наблюдаемой реакции.
- **Попарное тестирование:** для `/customers` и `/shipments` использованы четыре набора (роль, маршрут, корректность токена): admin/customers/да, admin/shipments/нет, customer/customers/нет, customer/shipments/да. Набор покрывает каждую пару значений этих трёх параметров, но не заменяет проверку всех комбинаций и остальных ролей.

Неизвестные бизнес-правила переходов не предполагаются тестами.
